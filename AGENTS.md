# bendsidecar — конвенции для агентов

Go-обвязка над Bend 2. Bend здесь исполняется как отдельный процесс, никогда иначе.

## Границы

- Публичный API — только в корневом пакете (`sidecar.go`, `build.go`, `doc.go`). Внутренности не экспортируются.
- Всё, что означает «запустить Bend», живёт в `Call`: один вызов = один процесс. **Не** добавляй пул процессов, переиспользование или in-process вызов через cgo: рантайм Bend течёт (~4 MB на прогон) и падает через `abort()`.
- Любая новая опция — это `Option`, а не поле структуры наружу.

## Обязательное

- Два транспорта, и оба проверены тестами: `Call` (argv → stdout, потолок ARG_MAX) и `CallFiles` (каталог с `in.bin`, ответ в `out.bin`, размер не ограничен). Не «улучшай» один за счёт другого и не переноси полезную нагрузку в argv, когда она больше пары килобайт.
- Ни одно изменение не принимается без `go vet ./... && go test ./...` (9 тестов, реальные сборки Bend).
- Тесты, которым нужен `bend`, обязаны `t.Skip`, если компилятора нет на PATH.
- Ошибки — только `*bendsidecar.Error` с `Kind`: новый вид отказа = новый `Kind`, а не строка в тексте.
- Ничего из окружения родителя не передаётся ребёнку: только `PATH`, `HOME` и явный `Env(...)`.
- Секреты в argv не передаются никогда — они видны в `/proc`.

## Чего не делать

- Не тащить зависимости: только stdlib.
- Не обещать в документации гарантий из `LAWS.bend`: доказательство не покрывает C-границу, argv и выход.
- Не пытаться ограничить память через `ulimit -v`: Bend резервирует терабайты VA. Память — cgroup или systemd-slice, и это дело вызывающей стороны.

## Проверка

```sh
gofmt -l . && go vet ./... && go test ./... -count=1
```
